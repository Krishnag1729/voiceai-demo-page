Defending VoiceAI

An offline English → Hindi voice translator (faster-whisper → NLLB/Opus-MT → MMS-TTS, Gradio UI). Likely questions a reviewer would ask, with answers grounded in this repo's SPEC.md, NOTES.md, PLAN.md and EDGE-DECISION.md.

Product & scope

Q1 What does this project actually do, end to end?

A local desktop app: the user speaks or types English, the app shows the transcribed English text, translates it to Hindi (Devanagari), and speaks the Hindi aloud. After a one-time download_models.py run, it works with no internet connection at all. The UI is a Gradio page at 127.0.0.1:7860, and the pipeline is speech-to-text (faster-whisper) → translation (NLLB-200 or Opus-MT) → text-to-speech (MMS-TTS Hindi).

Q2 Why English → Hindi specifically, and why offline?

Offline was a hard requirement from the start (SPEC §2, G3): no per-call API cost, no latency to a remote server, no audio leaving the machine, and it keeps working without connectivity — important once the same translation stack was later carried onto a phone (SPEC-edge.md). English→Hindi was chosen as the single language pair to get right rather than building a shallow multi-language system; the non-goals explicitly rule out other language pairs, cloud deployment, accounts, and training.

Q3 What was deliberately left out, and why?

Streaming/real-time simultaneous translation on desktop, Hindi→English, multi-user accounts, and model fine-tuning. Each adds real complexity (streaming needs sentence-boundary detection mid-speech, fine-tuning needs a training pipeline and eval set) that wasn't needed to prove the core idea: a clean, testable, fully offline translate-and-speak pipeline on a normal CPU laptop.

Architecture

Q4 Walk me through the architecture.

app.py (Gradio UI and event handlers) calls core/pipeline.py's Pipeline.run_audio() / run_text(), which fans out to three independent modules: core/stt.py (Whisper), core/translate.py (NLLB or Opus-MT), and core/tts.py (MMS-TTS). A fourth module, core/text_utils.py, is pure Python with no ML imports — sentence splitting, Hindi number-to-words, and TTS text normalization — and sits underneath translate/tts rather than beside them. core/config.py resolves settings from env vars and CLI flags.

Q5 Why dependency injection for Pipeline?

Pipeline receives its STT/translate/TTS components through its constructor instead of constructing them itself. That means unit tests (tests/conftest.py) can inject fakes and exercise all the branching logic — sentence splitting, number normalization, error paths — without ever loading a multi-GB model. It's also why Pipeline(stt=None) works for text-only use (the CLI's --text mode): the component simply isn't needed, so it isn't loaded.

Q6 Why does core/text_utils.py have to stay free of ML imports?

It's the highest-leverage code to get wrong silently (a missed decimal in sentence splitting, a bad number-to-words conversion) and the cheapest to test exhaustively, because it's pure Python. Keeping ML imports out of it means the full test_text_utils.py suite runs in milliseconds, with no model weights anywhere near it — a hard boundary enforced by project convention, not just a style choice.

Model choices & tradeoffs

Q7 Why NLLB-200-distilled-600M as the default translator, with Opus-MT as a "Fast" mode?

It's a quality/speed tradeoff, offered explicitly as two modes rather than hidden behind one choice. NLLB is the stronger general-purpose translator; later measurement on the phone track (EDGE-DECISION.md) found Opus-MT scoring roughly 19 chrF++ points below NLLB on IITB (29.8 vs 48.6) — not something int8 quantization or greedy decoding explained, it's the model itself. Opus-MT still earns its place as the fast path: it's a smaller Marian model with no language-token bookkeeping, useful when latency matters more than nuance.

Q8 Why faster-whisper (small.en) instead of plain Whisper or a bigger model?

faster-whisper is a CTranslate2 reimplementation of Whisper that runs int8 on CPU with no GPU required (SPEC §4, G4), and it bundles its own audio decoding via PyAV, so the app needs no system ffmpeg install. small.en is the size/accuracy point chosen for a normal laptop; on the phone track a different model (Moonshine) was chosen instead, because the constraints there — RAM, disk, battery — are different (see Q12).

Q9 Why MMS-TTS for the Hindi voice?

facebook/mms-tts-hin loads through transformers.VitsModel with no extra runtime dependency beyond what NLLB and Whisper already need — one framework (PyTorch/transformers) for every stage except faster-whisper's own CTranslate2 backend. It outputs a raw float waveform; the sample rate comes from model.config.sampling_rate rather than being hardcoded.

Q10 What are the licensing implications of these choices?

Whisper/faster-whisper is MIT and Opus-MT is Apache-2.0 — both fine for any use. NLLB-200 and MMS-TTS are CC-BY-NC 4.0, non-commercial only. That's a real constraint if this ever became a commercial product: the default (NLLB + MMS-TTS) would need to be swapped for permissively licensed alternatives, or the project would need to stay non-commercial. This is recorded in SPEC §4 precisely so it isn't discovered late.

Engineering practice

Q11 The spec and the libraries didn't always agree — how was that handled?

The project's own rule (CLAUDE.md, SPEC.md preamble): when the spec and an installed library disagree, trust the library and log the deviation in NOTES.md. Concrete examples from that log:

  • Gradio 6.x changed its buttons=["copy","download"] API from what 5.x had.
  • transformers 5.17's NLLB tokenizer takes src_lang="eng_Latn" at construction, not per-call.
  • PyAV 19 broke faster-whisper 1.2.1 on a fresh Linux install (decode_audio passed a keyword PyAV 19 no longer accepts). Typed-text input still worked, so only the audio-path integration test caught it; the fix was pinning av>=12,<19 in requirements.txt.

Q12 What's the subtlest bug you had to track down?

Loading NLLB or Opus-MT by repo id while online made transformers 5.x silently fetch a community-converted model.safetensors from a Hub pull-request branch in a background thread — sometimes after the model had already loaded from the local .bin, which both defeats "offline after first download" and wastes 2.4 GB of bandwidth. The fix was loading from the resolved local cache snapshot path rather than the repo id (resolve_model_path()), with an env var as a second guard. It only showed up because the offline-mode acceptance test (SPEC NF4) actually disabled the network and watched what happened.

Q13 How do you test an ML pipeline without downloading models in every test run?

Two tiers, split by a pytest marker: pytest -m "not slow" runs against the fakes in tests/conftest.py (no network, no weights, fast enough for every commit), and pytest -m slow runs the real models after download_models.py — that's what actually proves STT/MT/TTS behave correctly together. Dependency injection (Q5) is what makes the fast tier possible at all; without it, every pipeline test would need real models loaded.

Mobile / edge extension

Q14 The spec lists "mobile app" as a non-goal — why is there an android/ folder?

Scope grew after the desktop app was working. SPEC.md's own scope note (2026-10-23) says it covers only the desktop app and that the project later grew under separate specs: SPEC-edge.md / SPEC-android.md for the phone, SPEC-speed.md / SPEC-hw.md for speed, SPEC-size.md for APK size. The phone stack was proposed, measured against budget numbers, and explicitly approved by the user before being built (EDGE-DECISION.md, "Status: APPROVED").

Q15 The phone can't run NLLB-600M — what replaced it, and how did that turn out?

Moonshine base (int8, via sherpa-onnx) for speech-to-text, an in-house int8 ONNX export of IndicTrans2's 200M distilled model for translation, and Piper (also sherpa-onnx) for speech. The interesting result: the IndicTrans2 export didn't just fit the phone's budget, it beat the desktop's NLLB-600M on translation quality — 51.3 vs 48.6 chrF++ on IITB — while running in about 0.07 s per phrase instead of NLLB's cost on CPU. Opus-MT, the only other small off-the-shelf option, was ruled out for being ~19 points worse (Q7). It's a case where a model purpose-built for Indic languages outperformed a larger general multilingual one.

Deployment for this submission

Q16 The whole point of this app is "runs offline on your own laptop" — so what does "deployed URL" even mean here?

Honestly: there's a bit of tension between the spec's goal (no server, no cloud, fully local) and a course's expectation of a URL that always answers. The approach taken: a small, stable GitHub Pages page is the submitted URL. It reads a live.json file and points at whatever Gradio --share tunnel URL is currently active on the host machine running app.py — so the link in the submission form never changes, even though the actual tunnel URL does every time the app restarts. A helper script (scripts/go_live.sh) starts the app, captures the new tunnel URL, and pushes the update. The honest caveat is in the page itself: it only works while that machine is on and the app is running.

Q17 What would a "real" cloud deployment require instead?

Dropping the offline-first assumptions that shape most of the design: a server that stays warm (today the app lazy-loads the quality translator on first use and expects to run once, locally), some form of request isolation/rate limiting, and a hard look at the CC-BY-NC license on NLLB and MMS-TTS (Q10) before using them in anything resembling a hosted service for others. CPU inference latency under concurrent load would also need revisiting — the current numbers all assume one user on one machine.

Process & working with Claude Code

Q18 How was this actually built — what was the workflow?

Spec-driven: SPEC.md is the source of truth, PLAN.md turns it into ordered milestones with checkboxes, and every milestone ends with tests, lint, a NOTES.md entry for anything that deviated from plan, and a commit (Mx: <summary>). The build stops at every 🧑 human-check milestone — e.g. actually listening to the Hindi audio, or trying the mic in a browser — rather than assuming something sounds right. That discipline is also why the 8-session build (spanning about three weeks) could pick back up cold each time: the state that mattered was written down in files, not held in memory between sessions.
